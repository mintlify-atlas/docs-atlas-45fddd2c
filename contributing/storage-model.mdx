Reflect's storage model has exactly two layers: **Markdown files** that are the durable source of truth, and a **SQLite index** that is a rebuildable projection of those files. Understanding which layer owns what — and why — is essential context for any work on the indexer, sync adapter, or AI subsystem.

<Note>
The SQLite index is always rebuildable from your Markdown files. The only sanctioned exception is the `chat_*` tables, which hold AI conversation history that cannot be derived from Markdown. Any index wipe or rebuild operation must leave those tables untouched.
</Note>

## Layer 1: Markdown files

Markdown files are the user's durable, portable knowledge store. They can be inspected, edited, backed up, and version-controlled entirely outside Reflect. The app is designed so that deleting the SQLite index never loses note content.

### Directory layout

A Reflect graph folder follows this structure:

```text
my-notes/
├── daily/
│   └── 2025-11-04.md       # Daily notes: daily/YYYY-MM-DD.md
├── notes/
│   └── project-alpha.md    # Managed notes: notes/<slug>.md
├── assets/
│   └── screenshot.png      # Attachments referenced by relative links
├── audio-memos/
│   └── 2025-11-04-memo.webm # Raw audio recordings (durable artifact)
└── .reflect/               # Gitignored — SQLite index and local state
    ├── index.sqlite
    ├── inbox/              # Capture queue from the Chrome extension
    └── conflict-archive/   # Copies of conflicted file versions
```

### Note path conventions

Reflect distinguishes three kinds of notes by path:

| Kind | Path pattern | Rename behaviour |
|---|---|---|
| **Daily** | `daily/YYYY-MM-DD.md` | Never renamed; date is derived from the path |
| **Managed** | `notes/<slug>.md` | Slug is derived from the title and kept in sync |
| **Adopted** | Any path the user opened | Reflect edits in place and never renames the file |

### Frontmatter schema

Frontmatter is kept minimal. Only metadata that cannot be cleanly represented in Markdown goes here.

```yaml
---
id: 01j3z8qpk5m2n7x4vw6b9c0d1e   # Lowercase ULID — stable identity across renames
title: Project Alpha                # Overrides the H1-derived display title
aliases:                            # Alternative names for backlink resolution
  - Alpha
  - Project A
private: true                       # Hard block from all external services
---
```

**`id`** — A lowercase ULID generated when the note is created. It stays stable across file renames and is the canonical reference used internally by the backlink graph.

**`title`** — When present, this overrides the title derived from the first H1 heading. Useful for notes whose filename slug and heading diverge.

**`aliases`** — An array of alternative names. Backlink autocomplete and resolution checks aliases so that `[[Alpha]]` resolves to a note whose canonical title is "Project Alpha".

**`private: true`** — A hard block enforced via the `CloudSafe` type brand in `packages/core/src/ai/`. Content from a private note must never reach any external service: not an LLM, not a cloud transcription provider, not a sync relay. It is not a general encryption guarantee — the note is still locally searchable.

## Layer 2: SQLite index

The SQLite index lives at `<graph>/.reflect/index.sqlite`. It is a local projection layer that makes the app fast, searchable, and AI-ready. Everything in the index (except `chat_*` tables) can be reconstructed by re-parsing the Markdown files.

### What the index stores

<Accordion title="Note metadata and backlinks">
The `notes` table holds one row per Markdown file: path, title, note ID, timestamps, daily-note date, and a file hash used to detect changes. The `links` and `backlinks` tables form the incoming and outgoing backlink graph that powers `[[Wiki Link]]` resolution and the backlinks panel.
</Accordion>

<Accordion title="Full-text search (FTS5)">
The `search_fts` table is a SQLite FTS5 index over extracted plain text. It powers the instant lexical search that runs entirely on-device.
</Accordion>

<Accordion title="Semantic search (local ONNX)">
The `embedding_chunks` and `embedding_vectors` tables store note text split into sentence-aware chunks and their local vector embeddings. Embeddings are generated by a fastembed/ONNX model running in the Rust shell (outside the WebView), downloaded on demand. Chunks are content-hashed so unchanged text is never re-embedded.
</Accordion>

<Accordion title="Tags and aliases">
The `tags` and `aliases` tables are projections of frontmatter and inline content, used for autocomplete and backlink resolution.
</Accordion>

<Accordion title="File modification state and sync state">
The `sync_state` table stores adapter checkpoints and file versions. The file hash in `notes` lets the watcher skip files that have not changed since the last index pass.
</Accordion>

<Accordion title="AI chat history (non-rebuildable)">
The `chat_*` tables hold the full history of AI conversations. This is the one deliberate exception to the "projections only" rule — chat history is not derivable from Markdown, so it must survive any index wipe or schema migration. Never drop or truncate `chat_*` tables during a rebuild.
</Accordion>

### Shared schema crate

The SQLite schema is defined once in the `reflect-index-schema` Rust crate (`crates/index-schema/`). Both the desktop app (which writes the index) and the `reflect` CLI (which reads it) depend on this crate. Running migrations is handled by the desktop app; the CLI is read-only.

```text
crates/index-schema/   ← single set of SQLite migrations
        │
        ├── apps/desktop/src-tauri/   (writer: indexes, embeds, watcher)
        └── apps/cli/                 (reader: search, show, today)
```

## The `.reflect/` directory

`.reflect/` is an implementation detail of the running app, never a user data store.

```text
.reflect/
├── index.sqlite          # The projection database
├── inbox/                # Capture queue — items spooled by reflect-capture-host
└── conflict-archive/     # Copies of conflicted Markdown versions
```

**It is intentionally excluded from sync and backup:**

- Added to `.gitignore` automatically — it is never committed to the graph's Git/GitHub backup
- Marked local-only for iCloud Drive sync (`com.apple.icloud.desktop` xattr) so it does not leave the device
- Contains no durable user content (except `chat_*` — but those are scoped to the local device anyway)

<Tip>
You can safely delete `.reflect/index.sqlite` and reopen the graph in the desktop app to force a full index rebuild. The app detects the missing file on graph open and re-indexes every Markdown file from scratch. Chat history lives in its own `chat_*` tables; they are preserved separately from the projection tables and survive a forced rebuild.
</Tip>

## File watcher

The Rust `watcher` module (`apps/desktop/src-tauri/src/watcher.rs`) monitors the graph folder using the platform's native file-system event API (FSEvents on macOS). When files are created, modified, renamed, or deleted outside the app, the watcher emits events to the React frontend, which routes them to `@reflect/core` for incremental index updates.

The watcher is deliberately thin: it emits events and enqueues work, but never makes decisions about what to reindex. That policy lives in `@reflect/core`.

## Index rebuild

The index is rebuilt by **opening the graph in the desktop app** — not by running the CLI. The CLI is a read-only tool that queries an already-built index.

Rebuild is triggered automatically when:

- The graph is opened for the first time
- The app upgrades and the index schema version changes
- The user opens a graph whose index is missing or corrupt
- The Markdown parser or embedding model changes
- The user triggers a manual repair from the app

During a rebuild, the app walks all Markdown files, parses them with `@lezer/markdown`, and writes projection rows into SQLite. Embedding passes run in the background after the structural index is complete. The `chat_*` tables are left untouched throughout.
