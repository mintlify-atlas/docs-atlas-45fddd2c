Reflect's test suite is large — larger than you should attempt to run in full for every change. The rule is simple: **run only the tests that cover the code you touched.** This page explains the test architecture so you know exactly which commands to reach for.

## TypeScript tests with Vitest

Desktop TypeScript tests are split into two Vitest projects based on file extension:

<Tabs>
  <Tab title="*.test.tsx — browser project">
    Files ending in `.test.tsx` run in a **real browser** via Vitest's browser mode with [Playwright](https://playwright.dev) as the runner. Chromium is the default.

    ```bash
    # Run a specific browser test
    pnpm test --run path/to/component.test.tsx
    ```

    **Environment variables:**

    | Variable | Effect |
    |---|---|
    | `REFLECT_TEST_BROWSER=webkit` | Run in WebKit — the engine used by the production Tauri webview |
    | `DEBUG=1` | Open a headed (visible) browser window |

    **One-time setup** — install Playwright browsers before running `.test.tsx` files for the first time:

    ```bash
    pnpm --filter @reflect/desktop test:install
    ```

    Any test that drives the DOM, renders React components, or depends on browser APIs belongs in a `.test.tsx` file so it lands in this project.
  </Tab>
  <Tab title="*.test.ts — node project">
    Files ending in `.test.ts` run in **Node.js** — no browser, no DOM. Use this project for pure logic: parsing, graph algorithms, settings transforms, and anything that doesn't need a renderer.

    ```bash
    # Run a specific node test
    pnpm test --run path/to/logic.test.ts
    ```

    The distinction is intentional: `.test.ts` tests are fast and have no setup cost. If a test needs the DOM even slightly, rename it to `.test.tsx` so it runs in the browser project with real browser APIs.
  </Tab>
</Tabs>

<Note>
  `console.warn` and `console.error` calls **fail tests** via `vitest-fail-on-console`. Pre-existing noise is allowlisted in `apps/desktop/src/test-utils/allowed-console.ts`. PRs may only shrink that list — a new entry requires a stated reason explaining why the warning is expected and acceptable.
</Note>

## Running TypeScript tests

```bash
# Run one or more specific test files
pnpm test --run path/to/test

# Examples
pnpm test --run packages/core/src/markdown/parser.test.ts
pnpm test --run apps/desktop/src/components/Editor.test.tsx
```

Omit `--run` to enter watch mode (useful during active development on a single module).

## Rust tests

The Cargo workspace covers four crates: `reflect-open` (desktop shell), `reflect-cli`, `reflect-capture-host`, and `reflect-index-schema`. Prefer per-crate runs to avoid compiling everything:

```bash
# Test the CLI crate
cargo test -p reflect-cli

# Test the desktop Rust shell
cargo test -p reflect-open

# Test the entire workspace (stage sidecars first — see below)
pnpm --filter @reflect/desktop sidecar
cargo test --workspace
```

<Warning>
  Before running any `cargo build`, `cargo check`, `cargo test`, or `clippy` command that compiles the `reflect-open` desktop crate — including `--workspace` commands — you must stage the sidecar binaries once per checkout:

  ```bash
  pnpm --filter @reflect/desktop sidecar
  ```

  Without this, `tauri-build` fails with:
  ```
  resource path binaries/reflect-<triple> doesn't exist
  ```

  `pnpm tauri dev` and `pnpm tauri build` stage sidecars automatically, so this only applies to bare `cargo` invocations.
</Warning>

## The parity corpus

The `fixtures/parity/` directory keeps the TypeScript core and the Rust CLI in sync on Markdown parsing and data shape:

1. TypeScript generates `expected.json` from a set of canonical Markdown fixtures
2. Rust tests parse the same fixtures independently and assert that their output matches `expected.json`

This means **neither side can change its output without the other following in the same PR.** If you change a parsing rule in `packages/core`, the Rust tests in `apps/cli` will fail until you update the CLI to match — and vice versa. The parity corpus is the mechanism that prevents silent divergence between what the app indexes and what the CLI reads.

## Pre-merge checklist

Before declaring any work done and marking a PR ready for review:

```bash
pnpm typecheck          # must pass with zero errors
pnpm lint               # must pass; pnpm fix auto-corrects where possible
pnpm test --run <your test paths>
# if you touched Rust:
cargo test -p reflect-open   # or -p reflect-cli, depending on what changed
```

`pnpm check` runs `typecheck` and `lint` together as a single command.

<Tip>
  Write tests that document the **behavioral invariants** of what you added — not just happy-path coverage. A good test reads like a specification: if someone changes the behavior later, the test failure explains exactly what contract was broken.
</Tip>
